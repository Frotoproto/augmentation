# Implementation plan — Custom video player, interactive timeline, and elevated motion design

## Goal
Make the Augmentation Films site feel like a premium, cinematic portfolio. Replace the native browser video controls on every clip with a custom, on-brand player UI; turn the static `.timeline` into a truly interactive spine (clickable date markers that scroll-to and pulse, hover-driven video previews on the spine, animated progress fill that mirrors playback of the active clip); and push the overall animation language to a much higher level (smooth scroll-driven reveal, micro-interactions, easing, ambient glow, grain backdrop, and a magnetic custom cursor that reacts to interactive elements). Both `index.html` (dark) and `home1.html` (light) must ship the upgrade with matching behavior so the experience is consistent.

## Background and context
- Repo is a static 2-page portfolio. `index.html` + `styles.css` = dark theme; `home1.html` + `styles1.css` = light theme. The HTML bodies are identical except for the nav link target.
- All seven videos are referenced with native `<video controls>` and a single `<source>`. Each card lives in a `.container.right` with a `.title` and `.content` wrapper.
- Existing motion: `fadeIn`, `appear` (scroll-timeline blur-up), `borderGlow` on hover, custom blurred `.cursor` element, fixed nav that hides on scroll.
- Pain points today: native controls are visually inconsistent and do not match the dark/light theme; the timeline spine is invisible (`visibility: hidden` on `::after` and the dot markers); the only hover affordance is a scale + glow on the card; the custom cursor is a static blur that does not react; no playback-driven animation; no keyboard support on a "player".
- Files: `index.html`, `home1.html`, `styles.css`, `styles1.css`, plus binary assets (`*.mp4`, `fonts/Turnpike.ttf`, `grain.png`) that we will not modify.

## Files and areas
- `index.html` — remove native `controls` on every `<video>`, wrap each `.content` in a player shell that holds the custom UI (play/pause, scrubber, time, mute, fullscreen, big play overlay, hover preview), and add a script tag for the shared player + timeline script.
- `home1.html` — same structural upgrade as `index.html`; nav link target already points back to `index.html`.
- `styles.css` — full rewrite into a tokenized dark theme with a real timeline spine, a custom player, scroll/cursor interactions, and polished motion. CSS variables drive colors; the existing `appear` / `borderGlow` / `fadeIn` ideas are preserved and extended.
- `styles1.css` — full rewrite into a tokenized light theme that mirrors `styles.css` structure so the JS only needs one player class.
- `player.js` — new shared module loaded by both pages. Owns: building the custom UI per video, click-to-play/pause on the poster overlay, spacebar-to-toggle, scrubber drag + click-to-seek, mute toggle, fullscreen toggle, time formatting, progress reporting, "active video" pub/sub, intersection-observer to autoload metadata only on cards in view, and lightweight hover-preview (frame grab on mousemove within a 200 ms throttle, paused-at-time).
- `timeline.js` — new shared module: builds the spine markers from the existing `.container` list, click-to-scroll-into-view with a smooth eased scroll, marker pulse synced to which video is in the viewport, and a scrubber line that animates fill as the active video plays.
- `README.md` — short note about the new player (controls, keyboard, autoload strategy, theming tokens). Not a doc rewrite; just the section that explains the player.

No new binary assets. No backend, no framework, no build step. Pure HTML + CSS + vanilla JS committed directly so the static site continues to work when opened from disk or any static host.

## Implementation steps
1. **Theme tokens.** Define CSS custom properties for both themes (`--bg`, `--fg`, `--surface`, `--surface-2`, `--accent`, `--accent-2`, `--radius`, `--ease-out`, `--dur-fast/med/slow`, shadow stacks, font stacks, grain overlay URL). Reset box-sizing, set up a smooth-scroll root, set `cursor: none` on desktop and reveal native cursor on touch/`<= 900px`.
2. **Custom cursor v2.** Keep the blurred dot but add a second ring that follows with a transform-lerp each frame, and a `--cursor-scale` variable that grows over interactive elements (`.content`, `.timeline-marker`, `button`); hide it on touch.
3. **Timeline spine.** Draw a real vertical line (gradient + animated dash on scroll using a CSS scroll-linked animation on `background-position` or a transform on a pseudo). Render one marker per `.container` from JS, positioned along the spine using `getBoundingClientRect`. Markers: circle with the date label rotated 90°, hover scales the marker and shows a small play icon, click smooth-scrolls to the card center and pulses the marker. Active marker (card currently in viewport) is the `--accent` color and connects to the spine with a horizontal hairline.
4. **Cards.** Replace the static `.title` positioning with a real title bar inside the card (title, date, "play" pill). On scroll, cards reveal with a blur-up + translateY using IntersectionObserver so behavior is consistent with the new JS-driven spine (and is no longer dependent on `animation-timeline: view()` which has spotty support). Hover lifts the card with a layered shadow + accent border + a soft moving gradient sheen; focus state mirrors hover for keyboard users.
5. **Custom player shell (HTML structure per card).**
   ```
   <div class="content player" data-player>
     <video preload="metadata" playsinline>
       <source src="..." type="video/mp4">
     </video>
     <button class="player__big-play" aria-label="Play">▶</button>
     <div class="player__chrome" hidden>
       <button class="player__btn player__play" aria-label="Play/Pause"></button>
       <div class="player__time"><span class="player__current">0:00</span> / <span class="player__duration">0:00</span></div>
       <div class="player__scrubber" role="slider" aria-label="Seek" tabindex="0" aria-valuemin="0" aria-valuemax="100" aria-valuenow="0">
         <div class="player__scrubber-fill"></div>
         <div class="player__scrubber-buffer"></div>
         <div class="player__scrubber-thumb"></div>
       </div>
       <button class="player__btn player__mute" aria-label="Mute"></button>
       <button class="player__btn player__fs" aria-label="Fullscreen"></button>
     </div>
   </div>
   ```
6. **Custom player JS (`player.js`).** For each `[data-player]`:
   - Hide native `controls` (already removed in HTML), attach event listeners on the chrome buttons and the video element.
   - Big play overlay toggles to a "pause" state and starts playback; clicking the video itself also toggles play/pause.
   - Scrubber supports `pointerdown` + `pointermove` (pointer capture) for drag, click-to-seek, and keyboard `←/→` for ±5 s on the focused thumb.
   - Update `current`/`duration` text, fill width, and `aria-valuenow` on `timeupdate`. Update buffer bar from `progress` events.
   - Pause other videos when one starts (single-active behavior) and publish `player:playing` so the timeline can mark the active marker.
   - Mute toggle persists in `localStorage` under `aug:mute` so the choice is sticky across cards and pages.
   - Fullscreen uses the standard `requestFullscreen()` API; on enter, the chrome auto-hides after 2 s of no mouse movement and reappears on movement.
   - Hover-preview: when the video is paused and the user hovers the scrubber, show a small tooltip with the time the cursor is over; clicking seeks.
7. **Timeline JS (`timeline.js`).** Builds marker DOM from `.container` elements, computes positions after fonts load, and re-measures on resize (debounced). Uses IntersectionObserver with a rootMargin of `-40% 0% -40% 0%` to determine the "active" card and updates the active marker class. Subscribes to `player:playing` to mark the currently playing video; when its `timeupdate` fires, it animates a thin vertical bar on the spine that fills downward proportional to `currentTime / duration` (clamped to the marker span). Click marker → `el.scrollIntoView({ behavior: 'smooth', block: 'center' })` then trigger a one-shot pulse animation on the target card.
8. **Scroll polish.** Add a tiny `requestAnimationFrame`-driven parallax on the card thumbnails (max 8 px translate, never enough to feel gimmicky) and a `prefers-reduced-motion` guard that disables all of the above (cursor lerp, scroll-reveal, parallax, hover preview) — accessibility is part of "10× better".
9. **Nav.** Keep the existing hide-on-scroll behavior, but add a backdrop that fades instead of just turning off `backdrop-filter`, and add a focus ring that matches the accent.
10. **README note.** A small "Player" section listing controls, keyboard shortcuts, and the storage key.
11. **Verification.** See below.

## Edge cases and interactions
- Single-active playback: starting one video pauses any other. Confirmed by testing start of video B while A is playing.
- Scrubber while paused: drag still seeks. Scrubber while playing: drag seeks and keeps playing from the new time.
- Buffer bar before metadata loads: stays at 0% and grows as `progress` events arrive. Duration shows `--:--` until `loadedmetadata`.
- `prefers-reduced-motion: reduce` disables cursor lerp, parallax, hover preview, and the blur-up reveal; controls still work.
- Mobile (`<= 900px`): native cursor restored, markers collapse to a date strip under the nav, chrome buttons enlarge to a 44 px touch target, fullscreen still works.
- Keyboard: `Tab` order goes nav → card play → scrubber → mute → fullscreen. Spacebar on the player toggles play; `←/→` on the scrubber seeks ±5 s; `M` toggles mute; `F` toggles fullscreen.
- Autoload strategy: `preload="metadata"` so the first frame is cheap; IntersectionObserver sets `preload="auto"` on cards that are within 2 viewports of the current scroll, and resets to `metadata` on cards far away. This keeps the page light on slow connections.
- Mute preference persists across cards and pages via `localStorage`; missing or denied storage falls back to the in-memory default of `unmuted`.
- A11y: every chrome control has a visible focus ring (`outline: 2px solid var(--accent); outline-offset: 2px`) and an `aria-label`; the scrubber exposes `aria-valuenow`.
- File path safety: source `src` values already contain a space (`railer (1).mp4`) and a colon‑prefixed name (`Aug10-24.mp4`); do not rename them and do not change the case in the markup — just leave them as-is so playback keeps working.

## Verification
- `repo.html_validate` on `index.html` and `home1.html` after edits — must pass with no unmatched/closed tags.
- `repo.preview_page` on `index.html` and `home1.html` — must report all referenced local assets present (CSS, fonts, videos, grain). All 7 `<source>` paths must resolve.
- `repo.css_audit` and `repo.css_selectors` on `styles.css` and `styles1.css` — confirm no accidental duplicate selector groups, hardcoded colors only inside the theme token block, and that the player chrome selectors do not collide with the timeline selectors.
- `repo.run_checks` on the working branch for general config sanity.
- Visual smoke evidence: `repo.preview_page` returns the smoke check; this is static-asset existence, not a real browser render, so we will also use `repo.run_checks` and CSS audit as the completion-grade evidence (the container runner's standard static checks). We do not claim screenshot/lighthouse results unless a real backend reports them.
- Manual acceptance (described in the plan, not executed in this environment): open `index.html`, confirm all 7 videos play, pause, seek, mute, and fullscreen; confirm only one plays at a time; confirm the timeline markers reflect the active video and the click-to-scroll works; confirm the same on `home1.html` with the light palette; confirm `prefers-reduced-motion` disables motion; confirm `Tab`/`Space`/`←`/`→`/`M`/`F` shortcuts.

## Acceptance criteria (definition of done for Ultra Code)
- Every `<video>` on both pages renders the custom player chrome; no native browser controls are visible.
- Play, pause, seek (click + drag + keyboard), mute (sticky), and fullscreen all work on every video, on both pages.
- The timeline spine is visible, has one marker per video with the date label, and the active marker is highlighted; clicking a marker smooth-scrolls to its card.
- A small progress bar on the spine animates as the active video plays.
- Hovering a video card lifts it, glows, and shows a moving sheen; hovering a marker shows a play glyph.
- Custom cursor is a smooth two-element follower; scales up on interactive elements; hidden on touch.
- All new motion is guarded by `prefers-reduced-motion`.
- Both dark (`index.html` + `styles.css`) and light (`home1.html` + `styles1.css`) themes ship with the same capabilities and pass the same checks.
- `repo.html_validate`, `repo.preview_page`, `repo.css_audit`, `repo.css_selectors`, and `repo.run_checks` all pass on the working branch before the plan is closed.

## Risks and open questions
- **Risk:** removing native `controls` means iOS Safari may not show the system "play in fullscreen" affordance — mitigated by the in-player fullscreen button and `playsinline`.
- **Risk:** the new `player.js` and `timeline.js` must be loaded by both pages; if the script is `<script defer>` in the body it must run after the cards exist. We will use `<script src="player.js" defer></script>` and `<script src="timeline.js" defer></script>` placed just before `</body>`.
- **Risk:** the `data-player` selector is added during the HTML rewrite; the JS must tolerate pages where the card count differs (today both pages have 7, but the script should not hardcode 7). It will iterate over `[data-player]` and `[data-timeline-item]` at runtime.
- **Open question:** should the nav brand title also become a "skip to top" anchor on the dark page? Plan assumes yes — add `href="#top"` and an `id="top"` on the first card. If the user prefers the current `onclick`, we revert that part.

## Specialist team (Ultra Code, Orchestrator-led)
Selected for this task, with their explicit handoffs and quality gates:

- **Orchestrator** — owns the plan, sequences the work, blocks any specialist from committing changes that fail verification, and is the single point of accountability for closing the plan.
- **Product Analyst** — defines the exact UX moments the user must feel: "I can tell which video is playing from across the room," "clicking the spine is satisfying," "the cursor feels alive." Leaves a one-paragraph UX spec the Frontend Engineer uses as the source of truth.
- **Architect** — locks the file structure (`player.js`, `timeline.js`, themed CSS, HTML hooks `[data-player]` / `[data-timeline-item]`), chooses the CSS variable names that both themes share, and decides that the player class is identical across themes (only colors differ). Leaves a written contract for Frontend and Reviewer.
- **Frontend Engineering** — implements the HTML rewrite, the custom player UI, the timeline spine rendering, and the two theme stylesheets. Hands off: working files that pass `repo.html_validate`, `repo.css_audit`, and `repo.css_selectors`.
- **Accessibility** — owns the focus order, keyboard shortcuts, `aria-*` on the scrubber, reduced-motion media query, touch-vs-cursor handling, and contrast checks. Hands off: a checklist the Reviewer verifies line-by-line.
- **Performance** — owns the autoload strategy (preload="metadata" + IntersectionObserver upgrade), `requestAnimationFrame` for cursor lerp, throttled resize re-measure, and `prefers-reduced-motion` short-circuits. Hands off: a note for Frontend listing the exact listeners to throttle and the exact rAF loop to add.
- **Reviewer** — runs the verification suite (`repo.html_validate`, `repo.preview_page`, `repo.css_audit`, `repo.css_selectors`, `repo.run_checks`), diffs against the acceptance criteria, and is the only role that can move items to "done." This is the closing quality gate.
- **Documentation** — adds the short "Player" section to `README.md` (controls, keyboard, theming, the `aug:mute` storage key).

Backend, Databases, Cloudflare Platform, Reliability, Security, Dependency Engineering, Developer Experience, CI Agent, and Watcher roles were considered and not selected: the repo is a static client site with no build, no server, no deps, and no CI. Pulling in those specialists would not add evidence to the verification.

## Handoffs and quality gates
- Analyst → Frontend: UX spec must be written before the HTML rewrite begins.
- Architect → Frontend: token contract written before the CSS rewrite begins; Frontend must not invent new variable names.
- Frontend → Accessibility: when the HTML structure is final, Accessibility writes its checklist against the live DOM.
- Accessibility + Performance → Frontend: feedback merged into a single Frontend pass that also wires up `prefers-reduced-motion`.
- Frontend → Reviewer: a clean working branch with `index.html`, `home1.html`, `styles.css`, `styles1.css`, `player.js`, `timeline.js`, and the README change. Documentation ships in the same commit so Reviewer reviews one diff.
- Reviewer → Orchestrator: the only specialist that can flip a checklist item to "done." The plan is closed when every acceptance criterion is checked off AND every verification tool returns pass.
- Done conditions: all five verification tools pass on the working branch, both pages render the same player and spine, and the reduced-motion and keyboard behaviors are documented in the README.
- Blocked conditions: if any verification tool fails after one rerun, the plan goes blocked; the orchestrator writes the blocker (e.g., "CSS audit reports hardcoded color outside token block — line 142 of styles.css") instead of retrying silently.
